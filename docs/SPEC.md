## 1. Actors and browser profiles (five Chrome profiles, none signed in to Google; real platform passkeys)

- **Lea · phone** — owns the **phone key** (passkey #1 = the Safe's only owner). Mobile frame.
- **Lea · laptop** — holds the **Safety key**: a secp256k1 key generated with viem on first visit and stored in this profile's IndexedDB (prototype simplification, labelled; production: hardware-wallet key or PRF-encrypted key — not a passkey, which would be domain-bound). Exportable as a JSON file (Security centre → "Export Safety key") for the no-bank recovery CLI — prototype: plain JSON protected by file permissions; production: EIP-2335 / Web3 keystore v3 (no keystore library is installed and homemade encryption is banned, decided 6 Oct). Guardian 1. Also co-approves Tier-2 transfers: the laptop shows the request before signing.
- **Emergency card** — a secp256k1 key generated with viem during onboarding, shown once as QR + hex on a printable card, **never persisted by the app**. Guardian 2. Scanned/pasted on a new device during recovery.
- **Lea · new phone** — the replacement device after the loss.
- **Thief · stolen phone** — has the wallet URL and Lea's mock inbox, no passkey credential (represents failing biometrics).
- **Swissquote desk** — operator UI at `/desk`, behind an operator login (`DESK_OPERATOR_TOKEN`, SIMULATED SSO). **No function in the desk moves funds.**
- **sq-guardian** — process. Holds Swissquote's guardian key (guardian 3). Acts only on a bank-signed identity verdict + its own checks.
- **partner-guardian** — process, **assisted mode only, Wave 3 stretch**. Same code, own key and DB.

Guardian sets: default mode `{SafetyKey, EmergencyCard, Swissquote}`; assisted mode `{SafetyKey, Swissquote, Partner}` on the 14-day instance (demo uses the 3-minute instance for both if built). Threshold 2.

## 3. Flows (acceptance criteria = the demo)

### F1 Create wallet (Lea · phone, then laptop)
1. `/onboarding` step 1 — "Create your Keyline" → WebAuthn `create()` (platform authenticator, `userVerification: 'required'`, `residentKey: 'required'`). `POST /wallets` stores pubkey (x,y) + credentialId and returns the counterfactual Safe address (initial owner = WebAuthn shared signer; the first userOp deploys the passkey's `SafeWebAuthnSignerProxy` and swaps it in, so on Basescan the owner is the proxy from day 0; precompile verifier `0x100` set explicitly).
2. Step 2 — "Add your Safety key": phone shows a 6-digit pairing code; on *Lea · laptop* `/pair` enters it → the laptop generates its Safety key (viem) → `POST /wallets/:address/guardians {kind:'safety-key', address}` (bank-mediated pairing, SIMULATED).
3. Step 3 — "Print your Emergency card": generate a key with viem in the browser, render QR + hex + the sentence "This card cannot spend your money. It can only help restore access after a waiting period you will see." → user confirms "I stored it" → address registered as guardian; the private key is dropped from memory. (Demo prop: the presenter keeps the printed card / a text file *outside the app*, standing in for the drawer at home.)
4. Step 4 — Recovery mode: **Default** (recommended) vs **Assisted** (needs partner; explained; greyed out if not built).
5. Step 5 — "Protect my wallet": first sponsored userOp, batched: deploy Safe + `enableModule(recoveryModule)` + add the 3 guardians with threshold 2. Sponsored by the bank after `POST /policy/evaluate` (Tier 1, allowlisted self-call). **Signing order:** build userOp (dummy signature) → `POST /userops/sponsor` → passkey signs the SafeOp EIP-712 hash → `POST /userops/send`. Summary screen: "Protected: your phone key signs · 2 of 3 recoverers restore · Swissquote can't move your money alone."
6. Step 6 — "Prove ownership to Swissquote" (now that the Safe exists): sign the EIP-712 attestation `{clientId, wallet, chainId, nonce}` with the passkey through the Safe (ERC-1271 path) → `POST /attestations` → bank verifies with viem `verifyTypedData` → address bound to the KYC file and whitelisted both ways. Screen: "Ownership proven — Travel Rule check done. No screenshots."
7. Home: "Top up from my Swissquote account" → `POST /topups {amountUsdc}` → the bank's funder EOA sends USDC on-chain to the Safe (real tx; the account balance is SIMULATED). Copy: "Accepted instantly: this wallet is verified as yours." Activity shows the deposit.

### F2 Log in & sign (Lea · phone)
1. Login = WebAuthn `get()` (discoverable credential) → bank session (JWT 15 min, httpOnly).
2. Send → recipient (contacts; a new address shows a first-time notice) → amount in CHF with USDC secondary.
3. `POST /policy/evaluate` → decision. Tier 1: approve; review screen shows "What will happen" (simulation), screening ✓, "Network fee: paid by Swissquote". Tier 2 (above CHF 1'000/day): `step-up` — the laptop shows "Approve CHF 2'000 to Lukas Meier?" → Safety key signs the decision hash → `POST /policy/:id/step-up` → decision becomes approve (labelled policy-layer enforcement). Tier 3: `cooling` 60 s with Cancel. Block: reason, no button.
4. Build userOp → `POST /userops/sponsor {decisionId, userOp}` (bank attaches paymaster data only for a valid, unexpired decision whose calldata hash matches) → passkey signs SafeOp hash → `POST /userops/send` → poll `GET /userops/:hash`. Status: Signed → Sent → In block N → Confirmed, Basescan link. Activity row appears.
5. Negative paths: recipient = seeded sanctioned address → `block` ("Counterparty appears on the OFAC SDN list — simulated test entry"). `/dapps` → "DemoSwap" (allowlisted mock dApp, neutral name, in `policy/allowlist.json`) requests `approve(∞ USDC)` → decoded as danger with "Approve 100 USDC instead" → user picks the cap → Tier 1 approve. "Unknown dApp" → blocked, "Request review".

### F3 Lose the phone & recover (Lea · new phone + Lea · laptop)
1. `/recover` → "I lost my phone" → email code (SIMULATED inbox `/mock/inbox`) → identity check (SIMULATED swiyu e-ID form; persona rules §7; the desk operator can approve/refuse) → create the new passkey → `packages/chain.deploySignerProxy` → `POST /recoveries` (status `identity-pending` → `awaiting-guardians` once the verdict is `pass`).
2. Bank signs the `IdentityVerdict` → `POST sq-guardian /recoveries` → guardian validates the signature, mode and 24-h rule → signs/sends `confirmRecovery` (execute=false) → confirmation 1 recorded with tx hash.
3. Laptop shows "Restore access on a new phone? Requested 2 minutes ago from Zürich." → Safety key signs the module's EIP-712 recovery hash → `POST /recoveries/:id/confirm {kind:'safety-key', signature}` → bank relayer submits `multiConfirmRecovery([...], execute=true)` → **executed**, grace period starts (**decided 5 Oct 2026, Wave 0:** the deployed module v0.0.1 accepts `multiConfirmRecovery` with `(signer, signature)` pairs from any sender, EOA or ERC-1271, signers strictly ascending by address, empty `0x` signature = msg.sender confirms; the Safety key and Emergency card sign the module's EIP-712 `ExecuteRecovery(address wallet, address[] newOwners, uint256 newThreshold, uint256 nonce)` with domain `{name:'Social Recovery Module', version:'0.0.1', chainId, verifyingContract: module}`, nonce = `module.nonce(wallet)`; the bank relayer submits — see `docs/VERIFIED.md`).
4. New phone: countdown ring with the exact finalization time read from chain, caption "Waiting period accelerated for the demo: 3 min instead of 72 h". Desk shows states + audit log.
5. After the grace period: sq-guardian `finalizeRecovery` → new owner set, old passkey removed → "Welcome back, Lea" → F2 transfer proves control.

### F4 Attacker refused (Thief profile) — bonus
1. Thief opens the wallet → "This device has no key for this wallet." Send impossible.
2. Thief starts `/recover` → email code passes (he has the inbox) → identity check fails (persona rule; desk refuses) → `/refused`: "Recovery can't start: the identity check failed. The owner has been notified." Desk: `identity-refused` with reasons. Lea's devices: "Recovery attempt refused."
3. Desk "Override (demo: assume the bank was fooled)" → sq-guardian confirms alone → status stays `awaiting-guardians` ("Waiting for a second recoverer — Swissquote cannot finish this alone"). This is the on-chain proof.

### F4b Fraud while Lea still has her phone (variant, if time)
On a second wallet (or after F3): fraudster passes identity by override **and** pastes the Emergency card key → 2 of 3 → executed → Lea · phone alert "Recovery started from a new device — wasn't you?" → **Cancel recovery** (owner userOp via `buildCancelRecoveryUserOp`, sponsored) → `cancelled` on-chain; fraudster's screen: "Recovery cancelled by the owner."

### F5 Exit hatch (Security centre → "If Swissquote disappears")
Shows: the Safe address and guardian list with a Basescan link ("verify yourself"); "Your phone key keeps signing through any ERC-4337 bundler — toggle 'Pay my own fee'" (sends an unsponsored userOp if the Safe holds ETH; stretch); "Export Safety key" (JSON export; labelled prototype, production = encrypted keystore); "Your Safety key + your Emergency card restore access without Swissquote" with a CLI command shown (`pnpm keyline recover --without-bank --safety-key safety.json --emergency-card <hex>`); the honest caveat: "Passkeys are tied to this app's web address; in production the app is open source and the address is held by an independent escrow so it can't disappear with the bank."

### F6 Proof of ownership (Travel Rule)
Security centre → "Prove this wallet is yours" → signed EIP-712 proof for a chosen VASP → QR/text; `GET /attestations/:wallet`. Copy: "Swiss rules require platforms to verify who owns a wallet before sending to it. Share this proof instead of screenshots."

Guardian rules: verify `identityVerdict.signature` against `BANK_VERDICT_ADDRESS`; refuse `verdict !== 'pass'`; refuse if a recovery for this wallet was **executed** in the last 24 h (a merely confirmed-but-waiting or refused request does not count — the thief's overridden attempt must not block Lea's real one; an operator `refuse` supersedes any pending confirmation); read the guardian set from chain and refuse if this process is not a guardian of the wallet; never expose the key; log every decision. The partner guardian (assisted mode) runs its own simulated identity check and signs its own verdict rather than trusting the bank's.

## 7. Persona rules for simulated identity (bank)

`identity.ts`: case-insensitive — if `deviceLabel` contains `thief`, or the e-ID payload name ≠ client name → `fail` ("ID document name mismatch", "liveness check failed"); otherwise `pass`. Operator may `approve`/`refuse`/`override`. Every verdict is EIP-712-signed by `BANK_VERDICT_PRIVATE_KEY` and stored. README states that the thief persona is scripted.

## 11. WalletConnect — Keyline as a wallet for any EVM dApp (added 11 Oct 2026)

Keyline implements the **wallet side** of WalletConnect v2 with Reown WalletKit (`@reown/walletkit`, `@walletconnect/core`, `@walletconnect/utils`). Every dApp request goes through the same policy → simulation → screening → review → sponsor → passkey flow as an in-app transfer. WalletKit runs once per browser profile as a client-side singleton, and sessions persist in that profile's storage. The relay is a real third-party service (Reown), end-to-end encrypted. `NEXT_PUBLIC_REOWN_PROJECT_ID` holds the free Reown Cloud project id.

### 11.1 Session namespace
`eip155` with chain `eip155:84532` only, account `eip155:84532:<safe>`, events `accountsChanged`, `chainChanged`. Methods: `eth_sendTransaction`, `personal_sign`, `eth_signTypedData`, `eth_signTypedData_v4`, `eth_accounts`, `eth_chainId`, `wallet_switchEthereumChain` (any chain ≠ 84532 → error 4902 plus a sentence), and EIP-5792 `wallet_getCapabilities` (`atomicBatch: { supported: true }`, `paymasterService: { supported: true }` for 0x14a34), `wallet_sendCalls`, `wallet_getCallsStatus`. Refused with a plain-language reason: `eth_sign`, `eth_signTransaction` and any other method (`getSdkError('UNSUPPORTED_METHODS')`).

### 11.2 Requests
| Method | Flow | Result to the dApp |
|---|---|---|
| `eth_sendTransaction` | calls → `POST /policy/evaluate { kind: 'dapp', dappId: sessionTopic, origin, calls }` → review sheet → userOp → sponsor → passkey → send → inclusion | the **bundle transaction hash** from the userOp receipt (VERIFIED §20 records dApp-tracker behaviour and wait time) |

Declines answer `getSdkError('USER_REJECTED')`; policy blocks answer error 4001 with the policy reason. Requests past their WalletConnect expiry are shown as **expired**, never dropped silently.

### 11.3 Identity and policy (bank)
`POST /dapp-sessions` records each proposal and approval: topic, metadata (name, url, icons), origin and the Verify context (`validation: VALID|INVALID|UNKNOWN`, `isScam`). `DELETE /dapp-sessions/:topic` records a disconnect; `GET /dapp-sessions` lists sessions. Policy `kind: 'dapp'` gains these rules:
- allowlisted dApp → tier by amount, as today;
- verified but not allowlisted → Tier 2, with the policy line "First time with this app";
- `INVALID`, `isScam`, or origin ≠ metadata url → **block**: "This app's identity could not be verified". Such a proposal shows no Connect button.
- sanctioned counterparty anywhere in the calldata → block.
Gas: the bank sponsors any userOp the policy approved, whatever the dApp, within the daily cap. Every proposal, approval, refusal, request and disconnect is a bank event, and the desk shows them.
